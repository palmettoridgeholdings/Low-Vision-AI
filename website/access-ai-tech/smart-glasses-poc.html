Smart Glasses Proof of Concept

A vendor-neutral path for adding selective, user-triggered camera assistance after the native Android foundation is ready.

Current status: architecture and content design only. Access AI does not currently include a smart-glasses SDK, continuous capture, navigation, or obstacle avoidance.

Starting point

Build from the phone, not around a hardware vendor

Native Android is the primary mobile direction. A future glasses client should remain thin: capture only when requested, send a bounded request through a phone or controlled backend, and return concise speech or text.

Available baseline

Streamlit prototype

Demonstrates request handling for text, recorded audio, user-triggered still images, and spoken answers. It is not a glasses service or final mobile architecture.

Primary development path

Native Android

Establishes platform accessibility, on-device preferences, and a phone-based control surface before hardware integration is attempted.

Future adapter

Smart glasses

Add one vendor adapter at the edge only after its SDK, privacy behavior, accessibility, and operating cost are evaluated.

Selective-frame flow

Capture less, answer the task, then stop

1

User initiates capture

An explicit control starts one still-frame request. Audible or tactile feedback confirms capture and processing.

2

Phone or backend relays

The relay owns provider credentials, permission handling, resizing, timeouts, cancellation, and bounded retries.

3

Concise result returns

The user receives speech, captions, or phone text with explicit uncertainty. The capture is not retained by default.

Cost and privacy boundaries

A narrow first milestone

Selective frames reduce network traffic, provider usage, battery demand, and unnecessary capture compared with continuous video. Images should be resized to the minimum useful resolution for the task, and high-detail processing should be reserved for reading or close inspection.

  • No long-lived OpenAI key on glasses or in a mobile APK.
  • No background or continuous capture in the proposed first version.
  • No persistent capture archive by default.
  • No claim of safe navigation from a single camera response.
  • Every glasses action should have a phone and screen-reader equivalent.

Proposed sequence

Implementation gates

  1. Validate native Android onboarding, preferences, and accessibility on physical devices.
  2. Extract provider-independent request and response contracts without changing the working Streamlit flow.
  3. Test a local fake-device adapter with text and fixture images.
  4. Add an authenticated phone or backend relay with cancellation, timeouts, and deduplication.
  5. Evaluate one hardware adapter behind a feature flag.
  6. Conduct privacy, safety, accessibility, and usability testing before broader availability.
