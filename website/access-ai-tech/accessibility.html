Access AI policies

Accessibility Statement

Updated: September 5, 2026

Accessibility is the core purpose of Access AI. The project is being designed for blind and low-vision users first, with attention to screen readers, spoken interaction, Braille-compatible text entry, large controls, high contrast, and nonvisual descriptions.

Current status

Access AI is under active development. The public Streamlit application is a proof of concept for text, voice, camera, and accessibility concepts. Native Android is the primary mobile development direction so platform accessibility behavior can be implemented and physically tested.

This statement describes goals, current code, and known limitations. It is not a claim of formal WCAG, ADA, or other accessibility conformance.

Website accessibility

This static website package uses semantic landmarks and headings, a skip link, keyboard-visible focus, readable high-contrast colors, responsive layouts, and links with large activation areas. Real-world browser, zoom, screen-reader, forced-color, and mobile testing is still required after deployment.

Product accessibility goals

  • Complete onboarding without sighted assistance.
  • Support Android TalkBack and standard screen-reader gestures.
  • Provide clear control labels and logical focus order.
  • Support spoken setup and spoken answers when enabled.
  • Keep text input compatible with software keyboards and Braille input services.
  • Use large touch targets and readable high-contrast presentation.
  • Avoid essential tasks that depend only on color, imagery, drag gestures, or custom swipe gestures.
  • Use relative position, clock-face references, landmarks, and explicit uncertainty for nonvisual spatial descriptions when supported by the available image.

Testing

Automated accessibility checks are useful but are not proof of real-world usability. The repository uses code review and automated tests. Physical-device and assistive-technology checks remain required, including TalkBack testing before accessibility-sensitive Android milestones are considered complete.

The Streamlit proof of concept has browser and framework limitations. Its behavior should not be interpreted as the final native Android accessibility experience.

Known limitations

  • Browser-dependent speech and focus behavior in the Streamlit proof of concept.
  • Differences among screen readers, Android devices, speech engines, browsers, and Braille input services.
  • AI output that can be incomplete or inaccurate.
  • Features that depend on network, camera, microphone, or third-party AI availability.
  • Native Android camera, production voice recognition, and smart-glasses functions that remain development milestones rather than released capabilities.

Feedback

Accessibility feedback is welcome, including reports about labels, focus order, speech behavior, keyboard or Braille input, contrast, text scaling, and mobile usability.

Email founder@access-ai.tech. When possible, include the device, operating system, assistive technology, and the action you were trying to complete.

Commitment

Access AI will not claim formal accessibility conformance solely on the basis of automated testing. Public claims will remain proportional to the testing completed, and known limitations will be documented.
